# 案例复盘：《赤色要塞》UEFI 复刻

同目录的 `extraction-playbook.md`、`6502-quirks.md`、`verification.md` 都以"某项目"匿名引用案例，本文件是唯一具名的完整复盘：项目《赤色要塞》（Jackal）的 UEFI Shell 复刻，代码开源在 https://github.com/MikeWuPing/UEFI_Jackal。它服务两个用途——给 agent 当纵深案例教材，给技术写作当一手素材库。正文里每个数字、每个故事都能回到任务报告或项目台账的日期行复核；口径不一致处在原处标注，未经复核的推导一律加"约"。

**口径声明：案例的目标平台（UEFI + C）是该实例的实现细节，方法论与平台无关。** 本文出现的每个做法——声明式登记与机器校验、双侧 CRC 基线、锚定测试、注入输入加截图与日志的端到端闭环——换到 Windows、Linux、Android、Web，换成 Rust、JS、Kotlin，同样成立；需要替换的只有平台工具那几行。

## 1. 背景与规模

### 1.1 目标与输入

这是复刻，不是模拟：不写 NES 模拟器，不复刻 CPU/PPU/APU 的硬件行为，而是把原游戏的**逻辑**逐行从 6502 反汇编翻译成平台无关的 C 核心，把**资源**逐表从 ROM 里提取成语言中立的产物，再接到 UEFI 平台层上——GOP 帧缓冲做图形输出、UEFI 服务做键盘输入与帧节拍，在 QEMU 里原生运行。成品无声音：音效调用点保留等价的状态与时间行为，但不引入任何音频依赖。这个"逻辑翻译 + 资源提取"的取舍定下了整个项目的形状：没有 PPU 要仿真，但有装载链要镜像——因为游戏自己的代码就是这么把图形从 PRG 搬进 CHR RAM 的。

输入是一对素材：一个 iNES ROM（131088 字节 = 16 字节头 + 8 个 16KB PRG bank；CHR ROM size 为 0，mapper 2，垂直镜像；CRC32 = `0x6f5c75d2`），以及它的**全注释 6502 反汇编**（社区维护，MIT No Attribution 授权）。第二个输入的质量是本案例最大的效率变量，后文 §6 还会回到这一点：有标签名、有 RAM 符号表、有 `.PAD` 地址标注、数据区与代码区分开，等于把"找符号、分数据、猜地址"这三件最耗时的事预先做完了。CHR ROM 为 0 则决定了资源提取的形态——图案、调色板、关卡数据全在 PRG 里，想拿图必须镜像游戏自己的装载例程（load 表 → 段头 → RLE 流），从"CHR 区"直接读是读不到东西的。

最终交付是**单人模式**。双人模式的结构（输入合并、双人初始化、借命、槽位）都已实装，但 2P 滚动协同与 Label995 的双人段未实装，且 UEFI 单键盘恒映射 pad1——物理上无法双人游玩，双人可玩化记为未来工作。Level 4/5 的敌群按用户指示跳过；声音是 stub；POW 肖像的上下半反向滚动是已知的渲染差异。这些差异全部在代码注释与 README 里留痕——"与原版不同在哪、为什么"是可交付的一部分，不是可以省掉的脚注。

## 3. 技法实例

### 3.1 声明式清单与"元精灵组 2 物理乱序"

元精灵表配着指针表，本案例有低索引组与高索引组两张、各 128 个 `dw`。把清单登记成声明式条目（`{name, bank, cpu, kind, count, asm_ref, evidence}`）并加机器校验（指针回环：每个非零 `dw` 必须命中一条已登记条目的起始地址）之后，一个平时会被"第一个像的地方就登记"糊过去的问题被迫浮出水面：**顺序与边界的权威是谁？** 低索引组物理连续，从第一条目按 `1 + 4 × count` 走链 125 条，落点集合恰等于 ptr 表的 125 个不同 `dw` 值——一次走链同时证明了三件事：该组物理连续、该组 `dw` 没有漏项、高索引组的指针表就起在那个落点上。高索引组则完全相反：物理顺序与索引顺序不符（B5-B7 排在 B0-B4 之前、C9/CA 插在 B9 与 BA 之间），物理链中间还夹着 4 字节被反汇编标注为 `;Garbage data` 的填充——按链走会在那里把 `$F8` 读成"248 个精灵格"的计数，当场飞出数据区。

裁决是：**ptr 表 `dw` 是权威**，索引注释只当标签，地址排序只作物理排布参考。清单驱动的做法让这个裁决变成登记表里可复核的一行（`元精灵地址 = ptr dw`，两条 128 项表全部回环、244 张条目地址集合与 `dw` 集合完全相等），而不是散在脑子里的经验。它顺带带出两条"注释不是权威"的实证：一条元精灵的索引注释误写成 `;B4`（`dw` 表记的是 `;B5`）；一张联合索引注释 `;40 and 43` 说明**一个条目被多个索引共用是合法形态**——不要用注释重复当数据错误的证据。还有一处校准：`count` 的校验下界一开始写 1，实际原版有合法的空精灵条目（`db $00`），改成 0 是"修正规则对齐数据语义"，与"跑不过去就放宽"是两回事。

### 3.2 签名加代码引用：两把尺子交叉定位数据表

定位一张没有 `.PAD` 标注的表，最有力的组合是自下而上的**字节签名唯一性**与自上而下的**代码引用**。案例一：Bank6 有一张两字节表（`db $E0,$00`），字节对 `E0 00` 在该 bank 内命中两次（两个候选都落在合法数据区，周围字节没有异常）。裁决手段是反查操作数——把地址当绝对寻址指令的操作数扫全 PRG：`$A9B3` 的操作数字节对 `B3 A9`（即 `LDA $A9B3,Y`）在 `$A983` 出现且仅出现一次，而 `$B283` 的操作数字节对 `83 B2` 全 ROM 零次——没有任何代码读它。判决落定 `$A9B3`，结论可复核性极强：两个计数（1 与 0）是确定的，换个人重跑得同一个答案。

案例二暴露的是签名的长度纪律：load 表的开头六个字节（前两条目）看着已经很具体，实际在同一 bank 内命中 4 处——第 1/2/4/5 关的 load 表共享前两条目（公共文本、公共背景图案），要到第三个条目才分叉。**同族表往往共享表头若干条目，签名的长度必须跨过分叉点**，而分叉点在哪只能靠实测命中数试出来（这条教训的完整版本见 `extraction-playbook.md` §1.3）。两个案例合起来是同一条纪律的两面：签名证明"像"，代码引用证明"有人用它"；两把尺子都量过，定位才从"看起来对"变成"可复核"。

### 3.3 golden CRC 双侧一致：一次通过意味着什么

资源与渲染的搬运验证用**双侧 CRC**：Python oracle 脚本与 C 目标实现各自独立地按装载/渲染语义从 ROM 推导同一块内存，两侧对同一输入算 CRC32 比对。本案例三条基线——场景 6 的 pattern 装载进 CHR RAM 后 `0xdd6fe87e`、标题 nametable 解码写入后 `0xac986ad1`、标题帧 256x240 BGRX `0xaf23ce45`——C 侧全部**一次通过**；Phase 2 后期 Level 1 首屏的两张 nametable（`0xf51f1d64` / `0x8519f785`）同样一次对齐。

一次通过不是运气好，而是这条链的性质决定的含金量：两侧是**同一份 ASM 语义的两份独立实现**，端序、计数语义（0 按 256）、终止符集合、页基址、行地址步进任何一处理解不同，CRC 立刻分叉，而且分叉会指向具体的字节。它也确实抓过硬错误：oracle 初版按小端解读图案段头，解出越界地址 `$B002`（PPU 地址空间只到 `$3FFF`），当场暴露"图案段头大端、nametable 段小端"这对并存的约定——越界不是噪声，是端序猜错最干净的信号。使用纪律有三条：基线必须落盘可对比（清单侧在 `manifest.json`、oracle 侧在 golden 文件）、生成必须确定性（两跑字节一致）、**必须配非退化断言**（缓冲区非全零、帧非纯色）——否则全黑也能"通过"。

## 4. 代表性翻车与修复

### 4.1 双重偏移：`$39` 槽基与"合成环境掩盖"

**症状**：宿主单元测试全绿，QEMU 实机里吉普完全不能动。**根因**：碰撞查询例程在入口把 X 寄存器（吉普索引 0/1）加上 `$39`（精灵槽基址）定位槽位，调用方按 ASM 语义传的是**吉普索引**；初版 C 翻译传了槽位（`0x10+x`）。单元测试的合成环境里 `$39 = 0`，两种传法碰巧等价、全绿；真实关卡里 `$39 = $10`，索引被叠加两次，越出精灵槽数组，碰撞图读出垃圾。**修复**：调用点改回吉普索引。**锚定测试**：全链路用例 `gpm3_jeep_moves_right_on_beach`——从 GPM2 装载进入 GPM3（吉普从初始位置开始），按住 RIGHT 十帧断言位移与朝向，当场抓住并永久锚定。**留下的教训**：合成状态是测试自己造的，它掩盖的恰恰是环境依赖类缺陷；凡有真实路径可走，机制的最终证据必须来自真实环境用例（回查 task-3.9-report）。

### 4.2 潜伏的索引错误：L2-L6 首屏错用 L1 的表

**症状**：Level 2 首屏渲染为橄榄色斜纹乱码——**第一次玩到第二关才暴露**。**根因**：滚动装载选择 32x32 大 tile 定义表时，代码写成"表项 `level * 2`"，而取表助手内部已经做过 `* 2`；ASM 的 `LDA CurrentLevel / ASL / TAY` 语义是读表项 `[level]`。`level = 0` 时 `[0*2]` 与 `[0]` 恰好同值，**Level 1 永远正确，把缺陷掩盖了整三个 Phase**；`level = 1` 时错读表项 2（Level 3 的定义表地址）——Level 2 的全部大 tile 被错按 L1 的定义解码，Level 3-6 同理。**排查**：装载表、layout 表、定义表、调色板表、图案段逐一证伪后，用与 C 侧同构的仿真产出 Level 2 参考 CRC，再与宿主首屏逐字节对比，锁定到"定义表选择"那一行。**修复**：去掉多余的 `* 2`。**锚定测试**：`l2_first_screen_matches_golden`（两张 nametable 的 CRC 由独立仿真产出，`0xFD6FBB05` / `0x04D8118B`）。**留下的教训**：这类"只在特定输入上错"的索引错误，Phase 1 的静态检查看不见（地址全在合法窗口内），L1 结构校验零错误也不保证语义对——它只能靠"每个关卡都真的跑一遍"的锚定测试兜底（回查 task-6.5-report）。

### 4.3 快照晚了一拍：往返滚动才暴露的下行装载损坏

**症状**：用户自由驾驶上下往返后，地形与碰撞出现错位行——横向水带、炮台泡在水里、大门视觉与碰撞错位。**根因**：滚屏装载例程在下行分支要先取一份"当前屏幕状态"的快照再迁移指针；ASM 在 `Bank7.ASM:1801` 处取快照（页码递减之后、属性/图案地址与两个零页游标迁移**之前**），初版 C 把快照放在了整个迁移流程的末尾——下行装载的源页、源行、tile 地址全部晚了一拍。**排查路径本身值得记住**：上行装载追踪单调正确（看不出任何问题）→ 碰撞图逐槽与真地图比对（全等）→ **往返滚动**才把损坏变成可判定的差异。**修复**：把快照调用移回 `:1801` 的等价位置，余下的指针更新对下一帧生效。**锚定测试**：`down_scroll_load_roundtrip`——上滚到子位置 `$C2`、下滚回 `$AA`、再上滚回 `$C2`，往返后碰撞窗口逐字节一致。**留下的教训**：单向下行的用例测不出"快照晚一拍"，时序错误要靠**往返**才显形；这也是本案例里"用户试玩 → 锚定回归"闭环最典型的一次（回查 2026-07-22 台账条目）。

### 4.4 16 位借位链：右半图对象的可见性全反

**症状**：大门炸不开；屏上明明看得见的建筑与炮塔（屏 3 的大门、屏 2 的炮塔）不可见、不可击中、不开火。**根因**：精灵随滚动更新的位置例程里，横向"在屏判定"被译成单字节比较（低字节大于等于滚动值即算在屏）；ASM 原码是 16 位借位链——低字节相减后高字节还要 `SBC #$00` 传播借位，结果等于 0 才算落在当前屏页内。绝对坐标 `$100-$1FF`（右半图）的对象于是两种情形**全反**：低字节小的（真实在屏）被标成屏外，越出右缘的反被标在屏。**修复**：按借位链重写（`noBorrow = lb >= scroll`，`a = ub - (noBorrow ? 0 : 1)`，`a == 0` 且在屏页内才在屏，在屏位置取 `lb - scroll`、清屏外位）。**锚定测试**：`horiz_visibility_ub1_borrow_chain`（`$E0`/`$FF` 恰在屏、`$100`/`$140` 越界），外加端到端的大门手雷/火箭筒破门两例；连带修正了 Level 2/Level 6 测试里若干 `UB=1` 场景的布置错误——那些"以为在屏外"的测试场景其实全在屏内。**留下的教训**：`UB=1` 的对象是这类错误的专属试金石，修完要顺带审计所有同类用例的布置（回查 2026-07-22 台账条目）。

### 4.5 溅射速度未恢复：一发不"开花"的火箭弹

**症状**：火箭弹命中后没有开花效果——火焰窝在爆点，用户反馈"看不到爆炸"。**根因**：溅射状态机每帧移动之后，速度高字节要恢复成**未取反**的原值（ASM 是明确的一次读原值再写回）；初版 C 误把取反后的值存了回去，溅射速度高字节被困在 `±6` 的小循环里，振荡永远长不大，看上去就是"没炸开"。**修复**：恢复未取反值，修后振荡幅度逐帧递增（`+4, -6, +8 … ±40+`），原版的"开花"观感立刻回来。**锚定测试**：`bazooka_splash_oscillation_grows`（锚住 `±4/±6/±8` 三段幅度与状态字节翻转、高字节恢复值）。**排查插曲**：用户"看不到爆炸"的第一反应是渲染链出了问题，复核结论是渲染正常（宿主爆炸帧有 1467 个非黑像素、QEMU 抠图实证），之前观察不到是"溅射振幅 bug"叠加"截图间隔错过了约 0.65 秒的爆点窗口"——两个原因叠在一起，先怀疑了最花时间的那一个（回查 2026-07-22 台账条目）。

### 4.6 分派表错位与受阻转向缺失：四辆 boss 坦克的冻结与复活

**症状**：Level 1 boss 战的四辆坦克**全部冻结在屏幕边缘**，位置不变、不开火。**根因有两个，各自独立**。其一，精灵逻辑分派表在 `$27-$2F` 段集体错位——一处"占位修正"多写了一个条目，导致四个逻辑挂错档（本应指向"载入直升机""死亡生成 POW"等，全错挂或落空）；宿主测试此前**直调逻辑函数、不经过分派表**，所以这个错误在测试里完全不可见。其二，坦克转向例程缺了"受阻转向"段——碰撞后只清了速度，漏掉"碰撞标志非零则递减计时、计时归零则按扰动方向转向"的避障逻辑，坦克撞上东西就永远停住；boss 坦克状态机还漏了尾段的速度重算与状态推进。**修复**：修正分派表并全表核对 84 项；补齐受阻转向段与状态尾段。**结果**：QEMU 里坦克从全冻结到完全活过来——移动、开火、动画帧全部变化。**锚定测试**：`tank_turn_on_blocked`，以及 boss 坦克状态用例扩展为"受阻/畅通"双路。**留下的教训**：**绕过某一层的测试，测不到那一层**——直调函数的单测抓不住分派表错位，分派层要单独有测试；同时这段修复也说明"底层修好但上层调用点没修"的类错误，端到端画面观察是最快的发现通道（回查 task-4.12-report）。

## 5. 成本账

本案例的经济学口径来自用户记录：**约两天半的投入，用光两个 199 元档套餐的一周 Token 额度，其中一个不得不升级到 699 元档**。这笔账要拆开看才有意义——它买的不是一个"能跑的 demo"，而是 491 条可复核登记、约 160 项宿主锚定测试、48 项提取器回归、7 个端到端断言模式，以及一整套在交付后仍持续产出证据的验证设施。换言之，**Token 花在"证明自己没做错"上的比例，远高于花在"写代码"上**。

慢的原因有两笔，都可以客观归因。第一笔是持续自我验收：任务被规划为 7 个 Phase、54 个任务，每个任务自带步骤清单与验收点，任务完成后先验收再进入下一个，整个 Phase 结束还要再做一次总验收，中间不断插入测试用例——用户的原话是"他慢的一部分原因，也是因为他不停地在验证自己是不是做对了"。这不是流程冗余：本案例抓到的多数缺陷（双重偏移、分派表错位、借位链全反）都发生在"单测全绿"的假象之后，正是一次次把验证推到真实环境（宿主全链路 → QEMU 端到端）才暴露出来。第二笔是多模态读图：agent 靠截图"看"自己的产出——抽样渲染图核对提取质量，运行截图核对画面与阶段对应，观察驱动着下一轮修改；图像是 token 单价最高的输入，而闭环越完整，图看得越多。再叠加端到端验证本身的长跑成本（单轮 QEMU 自动验收跑 130 秒到 330 秒，截图几十张），账单的形状就解释清楚了。

对照产出，这笔账的结论可以写得更直白：用户对最终成品的评价是"基本上就一次通达，和原游戏基本上一模一样，我玩了几把，没有什么区别"。一次通达不是因为跳过了验证，恰恰是因为把验证铺满了全程——成本花在验证端，交付才落在"一模一样"上。

## 6. 结论：可复用的与不可复用的

可复用的东西有一组，它们之间是互相咬合的。**四条铁律**——证据优先（无出处数据不进产物）、翻译不重写（逐行对照、命名贴标签、偏差留痕）、校验报错修登记（绝不放宽闸门）、保真优先级（帧节拍 > 生成消亡 > 定点 > 碰撞 HP > 关卡推进 > 调色板图案 > 渲染效果）——决定了产物的可信度底座。**验证阶梯**（结构校验 → 双侧 CRC → 锚定测试 → 端到端闭环）给了每一级明确的证据形态与失败模式，并且有一条硬规矩：锚定测试必须"抓住过 bug"，从没失败过的测试只是烟雾。**多模态闭环**是 agent 在这个工作流里的能力面：注入输入（按键/触控）→ 截图与日志（看画面、读状态序列）→ 断言加多模态核对 → 发现问题回到代码——没有这双"眼睛和手"，本案例里那种"单测全绿、画面全错"的缺陷就只能等人来发现。还有两条小一点但很实用的：真实环境用例优于合成环境用例（`$39=0` 的教训）、往返/双向操作能暴露单向测试看不见的时序错误。

不可复用的部分同样要写清楚，否则复制的是一套幻觉。**本案例最大的外挂是全注释反汇编的输入质量**：标签名、RAM 符号表、`.PAD` 地址标注、数据区与代码区的分离，把符号追踪与地址推算这两件最耗时的事预先做完了；换成纯机器生成的反汇编，先要人机结合把数据从指令流里择出来，成本量级完全不同。其次是 ROM 形态的规整性——mapper 2、CHR 为 0、垂直镜像，窗口换算与装载链都相对简单，换成多窗口 mapper，地址换算层要重写（好在登记表记的是 `{bank, cpu}`，换算只有一处实现）。第三是平台的工具成熟度：本案例的闭环依赖 QEMU monitor 的截图与按键注入这类"agent 可直接驱动"的通道，换到闭环不成熟的平台，L4 这一级要自己搭。最后一处边界是人：自动化守住了回归，但新边界问题往往要真人起头——本案例 07-22 的整轮修复都由用户试玩报告触发；同时验收过程本身也需要人对画面做判断（"吉普不该停在树丛里"正是用户先看出来的）。把这三类前提讲明白，这套方法才是可迁移的：它把"像不像"翻译成"能不能被判据判定"，而判据的质量，最终仍然取决于素材、平台和你愿意为验证付出多少。
