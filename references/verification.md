# 保真验证阶梯实操

SKILL.md 的 §7 给出阶梯骨架：L1 结构校验 → L2 golden 基线 → L3 锚定测试 → L4 端到端闭环，下级不过不上级，每一级的证据必须是可引用、可复核的记录。本文是它的实操形态——每一级具体做什么、通过的证据长什么样、不通过时先查哪里，最后给出证据句式模板。

案例口径与 `references/extraction-playbook.md`、`references/6502-quirks.md` 相同：来自某次完整的 NES 复刻项目（下称"某项目"）。文中数值与行号落笔前已回证据源逐条复核；反汇编引用写成 `Bank7.ASM:1801` 这样的相对形式；目标平台的工具只给一行指路，不展开。

一条前提贯穿全文：**验证的对象是"画面与行为与预期一致"，不是"没报错"。** 进程退出码 0、构建通过、产物文件存在，只说明没崩——这些不是证据，只是继续验证的许可。

## 阶梯总览

| 级别 | 回答的问题 | 通过的证据形态 | 不通过时先查 |
|---|---|---|---|
| L1 结构校验 | 数据能被**正确地取出来**吗 | `validate_registry` 的**空错误列表** | 登记（地址/长度/条目数），不是校验器 |
| L2 golden 基线 | 搬运与装载**有没有走样** | 同一输入的 CRC 在独立两侧相等 | 两侧各自解码假设（端序、计数、终止符） |
| L3 锚定测试 | 每段逻辑**翻译对了吗** | 一机制一条测试全绿，且测试**抓住过 bug** | 用例是否走了真实路径（有无合成环境掩盖） |
| L4 端到端闭环 | 目标平台上**真的对了吗** | 截图 + 日志 + 断言，且版本对得上 | 采集通道与输入通道，最后才是应用逻辑 |

两级之间有一道明确的交接：L2 通过只证明"搬运无损"，语义正确性由 L3 兜底；L3 在宿主上通过不等于目标平台通过（渲染、输入、节拍都在平台层），那部分交给 L4。

## 1. L1 结构校验：证明"数据能正确取出来"

### 1.1 四件套与闸门形态

`validate_registry(rom, registry)` 返回错误字符串列表，**空列表才算通过**（SKILL.md §3.3）。四件套里三件机器判定、一件靠登记人手工核对：

- **边界**（机器）：bank 必须存在，cpu 必须落进该 bank 的合法窗口，且"偏移 + 条目长度"不越过 bank 末尾；
- **指针回环**（机器）：ptr_table 的每个非零 dw 都必须命中同组某条已登记条目的起始 cpu；
- **索引范围**（机器）：按格式给界，例如元精灵 count 在 0..64（OAM 只有 64 项）；
- **条目数对齐**（手工）：count 与反汇编里这张表的 `dw`/`db` 条目数逐个核对——机器手里没有反汇编，这一步只能人做，判据同样是"数出来的数字"。

管线入口把校验做成硬闸门：`run_extract.py` 拿到非空错误列表直接中止，**不产出任何产物**。错误信息逐条带 `name` 与 `asm_ref`，报错即回查那一行，不用满仓库找原因。校验跑通不是"没看见报错"，是零错误、输出为空列表。

### 1.2 报错时修登记，不放宽校验

校验器报错后的第一反应应当是回查登记，而不是把检查放宽一格。判断"这次到底该改谁"有一套三问，全部通过才允许动校验器本身：

- **数据证据驱动**：改动由 ROM/反汇编的实测事实引出，而不是"跑不过去"。某项目把元精灵 count 的下界从 1 放到 0，理由是原版确实有合法的空精灵条目（`db $00`），规则原本与数据语义不符；
- **闸门仍拦得住真错误**：改动后必须仍能挡住地址错、越界、漏登记。某项目把指针回环从"同 bank"扩到跨 bank 的全局地址集合，是因为 Bank7 的串接表确实指向 Bank4/5 的条目；扩展后指向未登记地址的指针依旧被拦，属修正而非放水；
- **留痕**：原因、证据、影响写进报告与代码注释。

通不过三问的"放宽"就是放水。而登记本身出错（地址错、bank 错、count 错、格式类别错）时动作只有一个：改登记，改完重跑 `validate_registry` 直到再次零错误——校验器是零假阴性闸门，闸门松一格，后面全部结论失去支撑。

### 1.3 反汇编注释与机器码冲突：回字节裁决

条目数对齐之外，地址本身也可能从注释里抄错。某项目的关卡对象生成地址表（关卡号 → 生成块指针），反汇编在这张表的定义处标了 `;$F15D`，实际那个地址是紧随其后的另一张表的起点；真正的主张来自读表指令的操作数字节 `B9 E0 F1`（即 `LDA $F1E0,Y`），登记改为 $F1E0 后走表用例立即正常。两处结论冲突时以机器码与 ROM 字节为准，注释只作提示（SKILL.md §2），并把这条勘误留痕。

这个案例的另一半更重要：**$F15D 这类错地址落在合法 bank 窗口内，L1 的边界检查抓不住它**——结构校验零错误只保证"数据能取出来"，不保证"取出来的是对的"。错地址最终是 L3 的走表用例当场抓住的（读到的"表头"是 0x0000，之后全是越界垃圾）。这就是阶梯分级的理由：L1 的出口不是"验证完成"，而是"可以开始 L2/L3"。

## 2. L2 golden 基线：证明"搬运与装载无走样"

### 2.1 双侧互证的两个方向

**清单侧（有登记条目的数据）**：`emit_c.py` 生成产物时给每条登记写 crc32 进 `assets/manifest.json`；目标实现拿到同一块数据后自己重算 crc32，与清单里的值比对。形状就是 SKILL.md §7 里的那几行：

```c
/* 目标实现侧：对生成的数组重算 CRC32，与 manifest.json 中该条目的 crc32 比对 */
uint32_t crc = crc32(rom_tblExampleLayout, (uint32_t)sizeof rom_tblExampleLayout);
```

**oracle 侧（没有清单条目的语义，如"装载进内存后的状态"）**：写一个独立脚本 oracle，直接从 ROM 按装载例程的语义重算，把结果落盘成 golden 基线；目标实现把数值抄成静态常量，用自己的 crc32 对同一块内存重算并断言相等。某项目的实例：oracle 脚本 `gen_golden.py` 独立算出三个基线，写进 golden JSON（`golden/ppu.json`）：

- 场景 6（标题）pattern 装载进 $0000-$1FFF 后的 crc32 = `0xdd6fe87e`；
- 标题 nametable 解码写入 $2000-$2FFF 后的 crc32 = `0xac986ad1`；
- 标题帧 256x240 BGRX 的 crc32 = `0xaf23ce45`（Python 渲染器与目标实现渲染器逐行同构）。

目标实现侧的断言长这样（数值是静态常量，重算用测试自带的 crc32，不复用被测代码）：

```c
CHECK(crc32_of(ChrRam, 0x2000)        == 0xDD6FE87Eu);  /* scene6 pattern */
CHECK(crc32_of(&ChrRam[0x2000], 0x1000) == 0xAC986AD1u);  /* title nametable */
```

这条链的性质是关键：Python 与 C 是**同一份 ASM 语义的两份独立实现**，任何一边把端序、计数、终止符理解错，CRC 立刻分叉。某项目标题帧的 crc 一次通过，等价于"两份独立渲染器逐字节一致"。若两侧只是从同一个 JSON 各读一遍，那是自己证自己，等于没有验证。

### 2.2 记录位置与回归用法

CRC 基线必须**落盘、可对比**，不能只在内存里算。清单侧在 `assets/manifest.json`（每条一个 `crc32` 字段，与 bin 产物同次生成）；oracle 侧在 golden JSON。使用方式：

- 任何改动（解码器、登记、ROM 换版本）后重跑提取，与基线逐条对比：数值不变 = 这块数据的字节没动；数值变化 = "字节动了"，必须能说清为什么（修了解码器/修了登记），说不清的变化就是回归事故；
- oracle 自身也要有回归：Python 侧测试重新从 ROM 推导一遍并与 JSON 比对，防止基线文件被手改后"基线跟着实现漂"；
- 确定生成是回归的前提：同一 ROM 两跑字节一致（固定顺序、固定换行、ASCII 输出），否则 CRC 对比全是噪声。

### 2.3 警惕双侧同错与"退化通过"

**双侧同错**：两侧若共用同一段错误假设，CRC 依然相等——所以"一侧通过"的准确含义是"翻译正确，**或者**两侧同错"，靠 L3/L4 兜底。某项目的 oracle 初版按小端解读 pattern 段头，解出的地址越界（$B002）当场暴露——pattern 段头是**大端**双字节（反汇编证据 `Bank3.ASM:8` 的 `db $02,$B0` 即 PPU 地址 $02B0），而 nametable 流是小端 dw，同 ROM 内两种端序并存。修正后两侧一致。这个错误能被抓住，靠的正是"两侧各自独立从 ROM 推导"。

**退化通过**：全零缓冲区、纯色帧也能算出 CRC 并"相等"。基线测试要配非退化断言：缓冲区非全零、帧不是纯色——否则"全黑也算过"。某项目的 golden 测试就显式断言场景 6 pattern 缓冲区非全零、标题帧非纯色。

L2 的边界写死一句话：**通过只证明搬运无损，语义正确性靠 L3/L4 兜底。**

## 3. L3 锚定测试：证明"翻译对了"

### 3.1 一机制一条，期望值从语义来

给每一段被翻译的逻辑机制挂一条测试：输入 → 期望输出。期望值的来源是汇编语义的推演与 L2 基线，不是"跑出来的值看着顺眼"——跑出来的值当期望，等于把现状固化成正确。测试名写清"谁在什么条件下应当怎样"，失败信息要能直接指向机制：某项目十六位借位链的用例命名 `horiz_visibility_ub1_borrow_chain`（$E0/$FF 恰在屏、$100/$140 越界），往返滚动的用例失败时打印首个差异偏移与新旧字节（`ROUNDTRIP DIFF @3xx: old -> new`）。

**锚定测试要抓住过 bug**：每修一个缺陷就补一条能复现它的测试；从没失败过的测试只是烟雾。

### 3.2 用真实环境用例，警惕合成环境掩盖

手工搭的最小合成状态（设几个变量就调用）经常缺掉真实运行的隐含前置条件，把缺陷掩盖成"通过"。三个真实案例：

**双重偏移被合成环境掩盖**。某项目碰撞查询例程在入口把 X（吉普索引 0/1）加上 `$39`（槽基）定位精灵槽（`Bank7.ASM:4470` 附近 `TXA / CLC / ADC $39 / TAX`），调用方按 ASM 语义传的是吉普索引；初版 C 翻译传了槽位（$10+x）。单测在"$39=0"的合成环境里碰巧等价、全绿；真实关卡里 $39=$10，索引被加两次（$10+x+$10=$20 起步）越出精灵槽数组范围，碰撞图越界读出垃圾——宿主单测全绿，实机上吉普完全动不了。抓住它的是走真实起步的全链路用例 `gpm3_jeep_moves_right_on_beach`：从 GPM2 装载进入 GPM3（吉普从初始位置开始），按住 RIGHT 十帧断言位移与朝向。**"$39=0 的合成环境"这类前置条件是测试自己造的，它掩盖的恰恰是环境依赖类缺陷。**

**缺失的开局初始化同样会掩盖**。另一条全链路用例（`gcs5_to_6_bullet_chain`：子弹命中 → 吉普死亡 → 命尽 → Game Over）直启 GPM3 时忘了补开局才设置的 1UP 阈值变量（阈值 0），首个得分即触发假 1UP、多出一条命，正好把"命尽 → 进入 Game Over"的路径盖掉。生产路径无 bug，是测试布置缺了真实前置——测试里必须补设，或干脆从真实入口走到底。

**单向序列看不出时序错误**。某项目下行滚屏的装载快照点错位：ASM 在 `Bank7.ASM:1801`（`DEC $4B` 之后、属性/tile 地址与 z4D/z4C 迁移**之前**）取快照，初版 C 把快照放在迁移全部完成之后，下行装载的源页/源行/tile 地址全错，玩家上下往返后地形与碰撞逐行错位。排查路径是：上行装载追踪（单调正确，看不出问题）→ 碰撞图逐槽与真地图比对 → **往返滚动暴露下行损坏**。锚定它的用例是 `down_scroll_load_roundtrip`：上滚到屏 2 子位置 $C2 → 下滚回 $AA → 再上滚回 $C2，往返后碰撞窗口逐字节一致。单向下行的用例测不出这类错误，往返才把"快照晚了一拍"变成可判定的差异。

结论性的做法：有真实路径可走就别拿合成状态替代；合成状态只配用在纯公式级（位运算、查表、单条公式）的小用例上，机制的最终证据必须来自真实环境用例。

### 3.3 L3 的边界

宿主上通过不等于目标平台上通过——渲染、输入、节拍都在平台层。把平台无关的核心逻辑做成能单独编译运行的模块，锚定测试跑在宿主或最快的可跑通道上；平台专属部分（呈现、输入、节拍）交给 L4。

## 4. L4 端到端闭环：证明"真机上真的对"

### 4.1 闭环四步（平台中立）

在目标平台上真跑：**运行目标实现 → 注入输入 → 截图/日志 → 多模态核对 + 断言**。原则只有一条——**输入要真的进到应用，画面要真的由应用产生**；工具按平台任选，能完成闭环即可。"目标平台"以交付形态为准：交付物本身就跑在虚拟机/模拟固件里（如配虚拟固件的 UEFI 应用），那个环境就是目标环境；把交付物换到别的环境里"代跑"才不算。

### 4.2 各平台工具一行指路

| 目标平台 | 输入注入 | 画面与日志采集 |
|---|---|---|
| Android | `adb shell input tap/text/keyevent` | `adb exec-out screencap -p` 抓图、`adb logcat` 收日志 |
| 桌面系统 | 系统自动化 API 注入按键/鼠标（X11 下 `xdotool` 一类） | 定时抓屏 + 应用自写日志/状态输出 |
| UEFI | QEMU monitor `sendkey` | QEMU monitor `screendump` 抓显存 + 串口日志（细节见 `emulator-uefi-shell-app` skill） |

这张表是例子不是白名单。两条通用要求：截图要抓**应用输出**而不是宿主窗口内容（窗口可能被遮挡或本身是黑）；应用要自己输出机器可读的日志（状态序列、事件、计数），串口、console、logcat 均可——**agent 的眼睛和耳朵都要有**。

### 4.3 编排：时间表注入 + 定时抓图 + 跑完自动断言

把闭环做成一条无人值守的命令：按键按时间表注入（第 t 秒按下某键并保持 x 毫秒），截图按固定间隔采集（如每秒一张，编号存档），跑完自动核对版本、错误行与状态序列，任一不符退出非零。断言分两层：

- **日志文本断言**：状态序列（某项目串口 STATE 行，如 `GCS 1→3→4→5`、`GPM 0→1→2→4→5→6→7→8→9→10→3` 覆盖 Chinook 入场全程）、事件与计数（`SPAWN id=01` 出现次数、`FIRE B0×1/A0×2` 追踪行）；
- **截图多模态核对**：见 §5。

**采样频率要与事件寿命匹配**。某项目 16 帧寿命的弹道在 1 秒间隔的截图里经常抓不到，改用串口 TRACE 作主证据、截图为辅；另一处"爆炸看起来没发生"，实为溅射速度 bug 与快照间隔错过约 0.65 秒的爆点窗口叠加——宿主爆炸帧有 1467 个非黑像素，"没截到"先是采样问题。没截到先调间隔、换事件触发截图，不要下"没发生"的结论。

### 4.4 输入注入的两个坑

**坑一：模拟输入不产生系统级自动重复。** 真实键盘按住会产生 OS 层 typematic 重复，脚本注入的"按住"不会。某项目在 QEMU 的 PS/2 通道上实测：`sendkey` 长按不复位，通道没有 typematic 重复，行为等价于"按了一下"——而同一脚本在带宿主的窗口模式下却"正常"，因为重复来自宿主 OS，掩盖了问题。对策：用连点模拟长按（如 0.3 秒间隔点按），把"长按 1.5 秒"翻译成一串点按；凡是验证依赖"按住"的量（位移距离、蓄力），先确认注入端确实产生了持续按下。

**坑二：先确认按键真的被应用收到。** 通道没通，后面所有断言都在验证一个"没被按过"的程序。最小自检用例：注入一个必然产生可观测状态的键，在日志里看到它引起的变化——某项目用"按退出键 → 串口出现 EXIT 标记"作为通道自检的最小用例，之后每一轮自动化都以这条自检开头。

### 4.5 验证钩子要隔离

为自动验收加的钩子（自动开始游戏、自动滚屏、无敌等）都是**非原版行为**：显式注释标注用途、用独立的构建输出目录编译，交付构建里不含。钩子还会改变画面，看到的"异常"要先排查钩子——某项目有一次截图里吉普停在绿色树丛中，看着像碰撞失效，实际是 AUTOSCROLL 钩子每帧强压位置驱动滚屏；碰撞语义本身忠实（树丛区碰撞类型为不可通行，已由宿主用例锚定）。钩子造成的假象查清后同样要固化（§5.4）。

## 5. 多模态核对 checklist

### 5.1 抽样图看什么

提取阶段的抽样渲染图（`render_png.py` 出的 tile/元精灵/关卡屏样本）与集成阶段的运行截图，看同样四件事：

- **形状可辨**：拼出来的图案不歪斜、不镜像、不整片错位；标题就该读出标题字样。某项目的标题画面核对到"标题字样的厂商标识与版权行、菜单选项全可辨"这一级；故事文本屏核对到"全文可读"；
- **颜色合理**：调色板正确、颜色数量与画面性质相符——单色、花屏、全屏一色都是坏信号；
- **与预期对象对应**：该阶段该出现的东西出现在预期位置（HUD、主角、敌人、地形），并且连续帧之间按状态机推进，不是同一张静止图；不同阶段的画面应当像素级不同；
- **与真值一致**：期望图与真实渲染冲突时，**以像素级真值（golden CRC）为准**。某项目计划里写"首屏中央土路、两侧丛林"，实际按滚动位置截到的是条带最左 256px（水域+滩缘+沙滩）——样本 PNG 是近似渲染，真值以 CRC 基线为准，截图用于管线核对。

**定量核对比"看着像"强**：某项目验证滚动装载时，对间隔约 0.9 秒（约 54 帧）的两张截图做沙地条带互相关——纵向位移 54px、重叠区平均差 0.0（逐像素无缝），把"新行装载正确"变成了数字。

### 5.2 直接判失败的信号

- **连续黑屏**：先怀疑采集通道本身（抓屏方式、渲染后缓冲、抓屏时机），别急着说"应用没画出来"。某项目的宿主窗口抓屏接连两轮不可用——一轮 40/40 全黑或混入窗口边框，另一轮 12/12 张是同一张无关图片（窗口被遮挡）；换成直取模拟器显存的抓屏通道后信号干净。窗口抓屏只适用于真实窗口场景；
- **版本/日志对不上**：截图/日志对应的产物版本与本次构建不一致，或日志里出现 ERROR 行——直接判失败，**不允许分析画面**（画面可能来自旧产物：静默编译失败的常见结果是旧二进制还在跑）。某项目的一次验证构建，构建脚本把两个验证宏并成一个非法宏名，钩子静默缺失；应用照常启动、行为等同普通构建（标题回环），串口状态序列只有 `GCS 1→2→0→1`、没有预期的进关序列，当场暴露；
- **图看不清 / 没截到 / 没跑到**：一律记"未验证"并继续查，不能按"应该没问题"放行。

### 5.3 版本水印：让"这张图是谁"可判定

截图判断"画面正确"的前置是"这张图来自本次构建"。做法是构建时生成版本号，应用启动时把版本+时间戳同时打到日志和画面固定角落；核对完版本一致再进画面分析。各平台的落点不同（日志通道加画面水印），与 §4.2 的工具指路同一处展开。

### 5.4 回归固化

多模态观察到的可疑现象，查清结论后要固化成断言：真缺陷 → 修完补一条能复现它的测试（§3.1）；假象 → 把"为什么是假象"写成一条测试。某项目把"树丛观察"固化成 `boss_screen_forest_collision_is_type1`：钉顶驱屏到 boss 锁滚，断言树丛条带与开阔沙地的碰撞类型单元格——下次同样的画面再出现，一条宿主用例就能证明引擎语义没变、要看的是驱动路径。

## 6. 证据纪律模板

### 6.1 合格句式：文件 + 位置 + 值 + 与期望的关系

- "`shot_012.png` 第 12 帧显示标题画面已出现（标题字样全可辨）。"
- "串口日志第 340 行 `STATE=2`；STATE 序列 `GCS 1→3→4→5` 与预期一致。"
- "`manifest.json` 中该条目的 `crc32` 与目标实现重算值相等（`0xDD6FE87E`）。"
- "帧缓冲 CRC 与 golden 相等（`0xaf23ce45`），Python 渲染器与 C 渲染器逐字节一致。"

形状归纳：**引用具体文件 → 定位（行号/帧号/条目名）→ 读出值 → 与期望的关系**。说不清位置的结论等于没验证。

### 6.2 禁止句式

- "应该没问题"、"看起来正常"、"大致对上了"——形容词不是证据；
- "你跑一下看看正不正常"——不许把验证外包给用户；agent 自己就能运行、截图、读日志，证据要自己拿出来。确实缺少运行条件时，明确标注"未验证"并给出验证步骤，而不是含糊的"已完成"；
- "构建通过了"、"进程退出码 0"、"产物文件存在"——跑通 ≠ 验证；
- "截图黑屏，应用可能没渲染"——先排除采集通道，再下结论；
- "TODO"、"见报告"、"某个脚本跑过"——不可复核，等于没写。

### 6.3 一个完整的证据段落

把上面的句式拼起来（数值取自某项目的一轮验证构建）：

> 运行验证构建（版本 `0.1.0+62`，串口 `APP_VERSION` 与构建时写入的期望版本一致，无 ERROR 行）。注入：`right` 两次长按、`z`/`x` 点按。日志：STATE 序列 `GCS 1→3→4→5`、`GPM 0→1→2→…→10→3`，覆盖关卡载入到可驾驶全程；`SPAWN id=01` 出现 2 次，与 Block1 的两项生成预期一致。截图：快照目录中 `026.png` 相对 `020.png` 吉普右移约 12px、朝向由 Up 转 Right；`063.png` 手雷高空帧（吉普上方飞行的小黑点）、`069.png` 低空本体帧（绿色雷体），与预期弹道一致。结论：移动、生成、武器三条链路端到端成立。

每一句都指得出文件与位置，第二个人可以重跑同一套注入复现——这就是这条阶梯要的证据。

## 结语

L1 保证取出的数据摆得正，L2 保证搬运与装载不丢字节，L3 保证每段逻辑按汇编语义在跑，L4 保证在目标平台上真的看得见、动得了。四级各有各的失败模式，也各有各的兜底对象：L1 的错误修登记，L2 的错误查两侧假设，L3 的错误查用例真实性，L4 的错误先查眼睛和手（采集通道、输入通道），再查应用。把这四步走完，留下的不是"我觉得没问题"，而是一串可以被人独立复核的文件、行号与数值——对逆向复刻这种"原作不会替你验收"的工作，这是唯一靠得住的完成定义。
